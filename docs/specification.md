# newsdesk: спецификация проекта (v0.1)

## 1. Цель
newsdesk принимает донесения от источников с разным доверием, объединяет их в сюжеты и решает, когда сюжет пора печатать. Это задание N6 "Издание" (системное программирование).из файла `docs/task.docx`

Входит в систему:
- сервер и клиент в одном бинарнике (newsdesk server и newsdesk client);
- рукопожатие, прием заметок с квитанциями, сюжеты, выпуск, статистика;
- доставка сообщений клиентам с нестабильной связью;
- хранение, переживающее перезапуск сервера.

Ограничения:
- саморегистрация клиентов (клиентов заводит редакция через конфиг);
- графический интерфейс (сервер и клиент консольные);

## 2. Термины
| Термин | Определение |
| --- | --- |
| Клиент | Источник донесений, заведенный редакцией. Имя, уровень (штатный / внештатный), доверие в [0, 1], роль |
| Редактор | Клиент с ролью `editor`: видит статистику всех, обычный клиент только свою |
| Заметка | Сообщение клиента с ключом сюжета, временем события и уникальным `note_id`. Принятые заметки хранятся в журнале и считаются в статистике |
| Сюжет | Один слух. Ключ = рубрика + точная формулировка темы |
| Вклад | Доверие клиента, добавленное к сюжету его первой принятой заметкой. Один клиент - один голос. Вклад клиента  уменьшается со временем с того момента, как произошло событие  |
| Квитанция | Ответ сервера на заметку: `accepted`, `duplicate` или `rejected` с причиной |
| Порядок подавших | Список клиентов сюжета по времени получения их первых принятых заметок. Фиксируется при выпуске |
| Ранг | Место клиента в порядке подавших (с 1) |
| Выпуск | Однократная необратимая печать сюжета, когда сумма вкладов >= порога |
| K | Число первых подавших, получающих поздравление при выпуске |
| Порог | Требуемое суммарное текущее доверие сюжета для выпуска |

## 3. Технические решения
 
Первая версия проекта пишется под Linux. 
Но архитектура строится так, чтобы перенос на macOS и Windows был не слишком трудным.
 | Область | Решение |
| --- | --- |
| Язык | C++17 |
| Платформа v1 | Linux |
| Сеть | Сырой TCP, неблокирующие сокеты |
| Мультиплексор | `poll()` в одном потоке |
| Потоки | Один поток, без мьютексов |
| Протокол | Строки с `\n`, каждая - JSON-объект |
| JSON | `nlohmann/json` (header-only) |
| Хранение | Журнал событий append-only + состояние в памяти |
| Время | `std::chrono::system_clock` |
| Сборка | CMake |
| Тесты | doctest |
| Конфиг | Файл JSON + аргументы командной строки |
| Клиент | Тот же бинарник, режим `client`, консольный |



## 4. Архитектура
 
Проект делится на платформо-независимые модули (логика) и один платформо-зависимый слой (`platform`). Все связанное с ОС лежит только там.


## 5. Конфигурация
Все параметры задает редакция в JSON-файле; одноименные аргументы командной строки имеют приоритет. 

| Параметр | По умолчанию | Смысл |
| --- | --- | --- |
| `threshold` | 0.75 | Порог суммарного доверия для выпуска |
| `congratulated_k` | 3 | Сколько первых подавших получают поздравление |
| `half_life_hours` | 6 | Период полураспада доверия сюжета |
| `listen` | `0.0.0.0:7000` | Адрес сервера |
| `journal_path` | `newsdesk.wal` | Путь к журналу |
| `clients` | - | Список клиентов: `id`, `trust`, `role` |
 
**Роли:** `reporter` (обычный клиент) и `editor` (видит всю статистику). Роль задается в конфиге, клиент сам не может ее повысить.

## 6. Модель данных
 
Состояние держится в памяти и восстанавливается чтением всех состояний из журнала.
 
| Сущность | Поля |
| --- | --- |
| Client | `id`, `trust`, `role`, `connected` (текущая сессия) |
| Note | `client_id`, `note_id`, `story_key`, `event_time`, `received_time`, `receipt` (сохраненный ответ, чтобы повторить его при дубле) |
| Story | `key` (рубрика + формулировка), `contributions[]`, `submitters[]` (порядок получения), `published` (флаг + время) |
| Contribution | `client_id`, `weight` (доверие на момент приема), `anchor_time` (от какого времени уменьшается contribution) |
| Outbox | на каждого клиента: очередь недоставленных сообщений с номерами, `last_acked` |
 
**Ключ сюжета** - нормализованная пара (рубрика, формулировка): обрезка пробелов по краям и сжатие повторных пробелов. Регистр сохраняется. Правило нормализации - допущение (раздел 11).
 
## 7. Протокол
 
Каждое сообщение - одна строка UTF-8, заканчивающаяся `\n`, с одним JSON-объектом. Поле `type` выбирает тип сообщения. Максимальная длина строки - 64 КБ; больше означает ошибку и разрыв соединения.
 
**Клиент -> сервер**
 
| type | Поля | До рукопожатия |
| --- | --- | --- |
| `hello` | `client_id`, `last_seq` (последний полученный номер сообщения) | разрешено |
| `note` | `note_id`, `rubric`, `topic`, `event_time` | отказ `not_authenticated` |
| `ack` | `seq` (подтверждение доставки) | отказ |
| `stats` | `client_id` (необязательно, только для `editor`; без него - своя статистика) | отказ |
| `bye` | - | разрешено |
 
**Сервер -> клиент**
 
| type | Поля | Назначение |
| --- | --- | --- |
| `welcome` | `client_id`, `role` | рукопожатие принято |
| `error` | `code`, `message` | рукопожатие отклонено (например неверный формат) |
| `receipt` | `note_id`, `status` (`accepted`, `duplicate`, `rejected`), `reason`? | квитанция на заметку |
| `congrats` | `seq`, `story`, `rank`, `text` | поздравление при выпуске (доставляется через очередь) |
| `stats` | статистика (см. раздел 9) | ответ на `stats` |
 
**Коды отказа** (поле `reason` в `receipt` или `code` в `error`):
- `not_authenticated`: рабочее сообщение до рукопожатия;
- `unknown_client`: клиента нет в реестре;
- `bad_format`: неверный JSON или недостающие поля;
- `forbidden`: запрос чужой статистики не редактором;
- `empty_story`: пустая рубрика или тема.


## 8. Обработка заметки
 
Заметка обрабатывается одной атомарной операцией в одном потоке.
 
1. Проверить, что рукопожатие выполнено. Иначе отказ `not_authenticated`.
2. Разобрать и проверить поля. Иначе отказ `bad_format` / `empty_story`.
3. Найти `(client_id, note_id)` в таблице обработанных. Если найдена, вернуть `duplicate` (без изменения состояния) и выйти.
4. Нормализовать ключ сюжета, найти или создать сюжет.
5. Время события в будущем ограничить временем получения.
6. Если сюжет уже напечатан, принять заметку без вклада; записать в журнал и вернуть `accepted`.
7. Если клиент уже давал вклад по этому сюжету, принять заметку без вклада и без изменения порядка.
8. Иначе добавить клиента в порядок подавших и вклад с весом, равным доверию клиента, и временем отсчета по событию заметки.
9. Посчитать сумму доверия сюжета на момент получения. Если сумма >= порога, выпустить сюжет (раздел 9).
10. Записать события в журнал (заметка, выпуск, поздравления), затем поместить квитанцию и поздравления в очереди и отправить.

**Повторы заметок:** повтор с тем же `(client_id, note_id)` возвращает `duplicate` и не меняет ни журнал, ни статистику, ни доверие сюжета. Отказ тоже запоминается, и повтор возвращает тот же отказ.
 
**Заметка "из прошлого":** принимается, но вклад тает от времени события, поэтому старый слух не оживляет сюжет. Порядок подавших по-прежнему определяется временем получения.
 
**Сюжет уже напечатан:** заметка записывается и считается принятой, но не дает голоса, ранга и попадания в статистику "в печати" (допущение, раздел 11).

## 9. Доверие, выпуск и статистика
 
Доверие сюжета считается по формуле на момент проверки. 
 
$$
T(s, t) = \sum_{i \in C(s)} w_i \cdot 2^{-(t - a_i)/H}
$$
 
где $C(s)$ - вклады сюжета $s$, $w_i$ - доверие клиента $i$, $a_i$ - время отсчета (время события заметки, не больше времени получения), $H$ - период полураспада (6 часов).
 
**Порог.** Проверяется только при приеме заметки, которая добавила вклад. Если T >= порога, сюжет выпускается. Между заметками доверие только убывает, поэтому фоновая проверка не нужна.
 
**Выпуск:**
- происходит ровно один раз на сюжет и не отменяется;
- порядок подавших (полный, а не только первые K) фиксируется в журнале;
- первые K клиентов получают "Поздравляем, ваша заметка попала в печать. Вы были N-м, кто сказал нам об этой новости." через очередь доставки.
**Ранг и вклад.** Ранг дает только первая принятая заметка клиента по сюжету; место в порядке определяется временем получения.
 
**Статистика по каждому клиенту:**
 
| Показатель | Как считается |
| --- | --- |
| `accepted` | число принятых заметок (без дублей и отказов) |
| `published` | число сюжетов, где у клиента есть ранг в напечатанном сюжете |
| `share` | `published / accepted` |
| `stories` | затронутые сюжеты |
| `scoops` |  напечатанные сюжеты, где клиент был первым |
| `avg_rank` | средний ранг по напечатанным сюжетам, где клиент подавал |
 
Свою статистику видит каждый клиент, статистику всех - только `editor`.

## 10. Доставка и персистентность
 
Сервер никогда не блокируется на медленном или офлайн-клиенте, а журнал позволяет пережить перезапуск.
 
**Доставка**
- у каждого клиента своя очередь исходящих сообщений с возрастающим `seq`;
- сокеты неблокирующие; сервер пишет в сокет только при готовности по `poll`, недописанное остается в буфере;
- на `hello` клиент передает `last_seq`, а сервер пересылает все, что номером больше;
- сообщения удаляются из очереди по подтверждению `ack`;
- лимит очереди и буфера задается в конфиге; при превышении сервер разрывает соединение, очередь сохраняется.
**Журнал**
- файл append-only, одна запись = одна строка JSON с номером и контрольной суммой;
- типы записей: `note` (заметка с квитанцией), `publish` (выпуск с полным порядком), `enqueue` (сообщение в очереди), `ack`;
- квитанция отправляется только после записи в журнал и `fsync` (через `platform::`);
- при старте журнал проигрывается с начала в тот же `engine`, что и при обычной работе, но со временем из записей;
- неполная последняя строка или неверная контрольная сумма отбрасывается с предупреждением, сервер запускается; повреждение в середине журнала - ошибка запуска.

## 11. Допущения 

| Вопрос | Решение по умолчанию |
| --- | --- |
| Значение порога | 0.75 |
| Вклад заметки "из прошлого" | Тает от времени события, не позже времени получения |
| Повтор отказа | Возвращается тот же отказ (сохраненный ответ) |
| Нормализация "точной формулировки" | Обрезка и сжатие пробелов, регистр сохраняется |
| Аутентификация | Только имя клиента из реестра, без пароля |
| Клиент прислал `last_seq` меньше серверного `last_acked` | Сервер шлет только то, что осталось в очереди, удаленное не восстанавливается |
| Смена доверия редакцией | Вступает в силу при перезапуске сервера, на уже внесенные вклады не влияет |
